Harness Structure and Run Flow

Folder layout, file layout, and the sequence one unit of clinical programming work follows from work order to release.

A harness is the controlled workplace a clinical programmer works inside. It does not replace the programmer and is not built to. The programmer holds the judgment — what the specification means, which derivation is right, whether a finding is a real defect or an explained exception, whether the output can be released. The harness holds everything around that judgment: the approved inputs, the pinned standards versions, the program, the SAS run, the checks, the findings, the reviewer's decision, and the evidence of what happened. The pairing is the product. The programmer reaches each decision sooner because setup, execution, checking and evidence capture are already done, and each decision is better supported because the harness can show exactly what it rested on.

SAS, the statistical software these programs run in, sits outside the harness. The harness submits an approved program to a licensed SAS environment and captures the result.

Division of labor

The programmer decides

  • What the specification means where it is silent or ambiguous
  • Which derivation is scientifically correct
  • Whether a finding is a real defect or an explained exception
  • Whether the deliverable is fit to release, and signs for it

The harness does

  • Freezes and hashes the inputs, pins the standards versions
  • Submits the program to SAS, captures log, datasets and reports
  • Runs the log rule pack, structural, terminology and comparison checks
  • Writes the run record and blocks release until a named human signs

How a unit runs

Figure 1 — The five steps of a unit run, the kernel service the programmer uses at each one, and the single run record they all append to. A finding at step 4 returns the unit to step 2: the SAS programmer corrects the program and re-runs, within the allowance set in the work order, with the frozen input hashes re-verified before each rerun. The assistant may draft the program at step 2; it holds no release credentials at step 5.

In a double-programmed unit, two programmers build the same deliverable independently from the same specification. The QC branch is a credential boundary, not a naming convention: the context that produces qc/adae_qc.sas cannot read production/adae.sas or its outputs. The evidence is the PROC COMPARE report (the SAS step that diffs two datasets), not either output.

What the run record holds

GroupRecorded for every execution
UnitStudy, deliverable, work-order version, declared dependencies.
InputsSHA-256 of every frozen dataset, specification, and macro consumed. Verified before any rerun.
StandardsSDTMIG, ADaMIG, Define-XML, controlled terminology package date, validator rule pack version, log rule pack version.
EnvironmentSAS version and hotfix level, operating system, encoding, locale, time zone, macro library commit, format catalog hash.
ExecutionStart, end, return code, resource usage.
ChecksLog findings by severity, structural and transport-format results, terminology results, comparison outcome.
OutputsPath and SHA-256 for every produced file.
AssistantTool name, model version, prompt-pack version. Recorded as provenance; never a source of verdicts.
ReviewReviewer, timestamp, disposition, release decision.

Order of deliverables

SourcesStudy inputs: protocol and SAP, annotated CRF (aCRF), EDC raw data, vendor transfers.
SDTMRegulator-ready tabulations: DM first, then trial design, domain families, SUPP-- and RELREC.
ADaMAnalysis-ready datasets: ADSL first, then ADAE, ADLB, ADVS, ADTTE and custom sets.
TLFThe report's tables, listings and figures, built against approved shells.
MetadataDefine-XML dictionaries for SDTM and ADaM, cSDRG and ADRG reviewer guides, aCRF.
SubmissionTechnical QC, final manifest, package released only on approval.

Editing any artifact marks every downstream artifact that references it stale in manifest.json and blocks release until it is re-run, re-checked and re-dispositioned.

Boundaries. The harness runs inside the client-approved environment. Blinded and unblinded work run as separate instances with separate credentials and evidence stores. The assistant never receives passwords, unblinding keys, or release credentials, and may draft only one side of a double-programmed unit. Without a reachable licensed SAS environment, the harness runs in simulation mode on synthetic or public fixture data, and every execution and validation status is marked untested.
